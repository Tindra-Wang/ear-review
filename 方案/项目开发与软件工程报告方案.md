# 蓝牙耳机评论分析与选购辅助系统：开发与软件工程报告方案

版本：v0.1，2026-10-12。

性质：实施前方案。本文的功能、规模与质量数字均为计划或目标，不代表已实现或实测结果。

已知约束：三人课程大作业；使用 TypeScript；技术栈自主选择。暂定普通 Windows 电脑、CPU、本地浏览器演示，开发周期约四周。期限、课程模板及是否强制深度学习待补充后调整。

## 1. 项目定位与软件工程方法

项目题目：《基于方面级情感分析的蓝牙耳机评论分析与选购辅助系统》。

业务目标：帮助用户从大量中文评论中了解不同耳机在具体评价方面的优缺点，并查看支持结论的原文。评价维度固定为音质、降噪、佩戴舒适度、续航、通话、游戏延迟六项。

核心处理对象为文本。评论导入、产品管理和图表是支撑功能；方面识别、方面情感分类、原文证据定位是 NLP 核心。选购辅助采用明确的需求维度与评论统计，不声称检测了耳机真实性能。

软件工程落实为六条规则：

1. 先确定用户、业务目标、系统边界，再选技术与模块。
2. 每项需求有编号、优先级、输入输出、约束、异常处理、验收方法。
3. 设计区分架构、模块、数据、接口和算法，不将页面截图当作详细设计。
4. 建立“需求编号 → 模块与接口 → 测试用例 → 实现证据 → 展示材料”的追踪记录。
5. 基线确定后记录需求变更及对实现、测试、数据和报告的影响。
6. 报告随开发积累，最终实现章节只描述实际完成内容，实验指标只使用实测结果。

参考 SWEBOK 公开知识体系、ISO/IEC/IEEE 29148 公开需求工程内容与 ISO/IEC 25010:2023 公开质量模型介绍；这是课程项目的裁剪方案，不宣称通过标准认证或已经验证全文符合性。

## 2. 需求边界

### 2.1 用户和利益相关者

- 普通浏览者：查看产品画像、筛选评论、对比产品；无需注册。
- 管理员/数据维护者：登录后管理产品、导入评论、运行分析、人工复核、导出结果。
- 开发团队：维护代码、标注规范、模型、测试和报告。
- 教师/验收者：从功能流程、NLP 效果、工程文档和演示证据判断完成情况。

前期建议访谈三位潜在使用者，并进行一次团队需求评审。访谈须实际实施后记录，当前不能写为“已完成用户调研”。重点确认用户关注的维度、原文追溯需求，以及空数据和样本不足时的期待。

### 2.2 范围内

- 中文文字评论，UTF-8 CSV 导入及单条文本体验。
- 首版覆盖 3～5 个型号，固定六项评价维度。
- 一条评论可涉及多个方面，每个方面单独判断。
- 情感标签为正面、负面、中性；同一方面出现相互冲突意见时汇总为混合。
- 未涉及某方面为“未提及”；无法可靠处理为“待复核”，二者均不能视作中性。
- 结果关联原始评论、模型版本和证据片段。
- 评论筛选、产品画像、2～3 款产品对比、管理员复核与结果导出。
- 通勤/游戏/长时间佩戴作为用户选择的需求预设，映射到相关维度。

### 2.3 范围外

- 电商实时爬虫、反爬处理、自动同步、价格追踪、支付与交易。
- 语音、图片评论、多语言、跨品类通用分析。
- 开放式聊天助手、通用知识库、长文生成。
- 实际声学测评、真假评论识别、商业推荐算法与大规模在线训练。
- 多租户、复杂注册体系、微服务、生产级高并发与高可用部署。

范围外事项不会阻止首版闭环完成。若课程明确要求其中某项，按需求变更处理。

### 2.4 输入与业务限制

- 评论必填字段：productId、reviewId、text；可选 reviewDate、source、sourceRef、rating。
- 首版单文件不超过 5 MB、单批最多 5,000 行、单条最多 1,000 个 Unicode 字符。超限明确报错，不静默截断。
- 不导入用户名、头像、电话等无关个人信息；来源与使用条件单独保存。
- 星级仅作展示或诊断字段，不作为方面标签的真值，也不输入分类器。
- 日期缺失不伪造日期；首版不承诺时间趋势功能。
- 正式评估数据与演示合成数据分离；没有可靠来源的数据不能标为真实消费者评论。

## 3. 功能需求基线

以下均为 P0 必做，首版优先形成完整闭环。每项需求将在需求规格说明书中进一步细化为用例。

### FR-01 产品管理与访问控制

管理员维护产品名称、型号和说明；浏览者只读。管理员登录后才能导入、启动分析、修改结果。未授权写入必须由后端拒绝，不能只隐藏按钮。首版一个管理员角色，无公开注册。

验收：合法登录成功，错误凭据失败，直接调用未授权写接口被拒绝；浏览者正常访问画像。

### FR-02 评论导入与校验

上传 CSV，先预览合法行、错误行和重复行，再提交。空评论、未知产品、重复 ID、长度超限须定位到行号。以产品及标准化文本指纹识别文本重复；原文保持不变。相同评论再次导入不重复计数。批次保存导入数量、拒绝原因和来源。

验收：使用混合合法/非法/重复行的固定文件验证计数；重复导入后有效评论数不增加；数据库事务保证提交失败不留下不完整批次。

### FR-03 分析任务与单条体验

批次创建持久化分析任务，显示待处理、运行中、完成、失败和处理数量。任务固定模型版本。批量工作在 Node Worker 中执行，避免阻塞接口。单条体验返回结构化分析结果，默认不写入正式统计。

验收：任务状态按合法路径变化；失败可重试且不重复生成有效结果；服务重启后旧运行任务标为中断/失败并允许显式重试，不伪装成完成。

### FR-04 方面级情感与原文证据

从文本识别六项方面，对每项输出情感、原文证据和处理状态。相邻正负意见必须分别关联对应方面，例如“音质很好，但戴久了耳朵疼”应有音质正面和舒适度负面。

证据必须为原文真实子串，并保存偏移。前后端统一使用 JavaScript UTF-16 起止索引，左闭右开；标准化文本另存映射，不能用清洗后索引直接截原文。原文高亮是判断依据展示，不等同于模型因果解释。

验收：证据子串与偏移一致；未提及不填补标签；不支持的含蓄、反讽或难以归属的表达允许待复核，并在算法评估中计入漏检或未覆盖。

### FR-05 评论浏览与复核

支持按产品、方面、情感、复核状态筛选，并分页查看。管理员可纠正方面及情感、调整证据，必须保留原预测、修改人、时间和理由。

验收：组合筛选正确；纠正后有效结果发生变化，原预测仍可查询；无权限人员不能修改；复核标签不能悄悄写回冻结测试集。

### FR-06 产品画像

每个方面展示提及评论数、正面/负面/中性/混合/待复核数及代表原文。采用“评论—方面”作为计数单位，同一条评论对同一方面最多计一次。

定义 N = 正面 + 负面 + 中性 + 混合的已判定评论数；正面评价占比 = 正面/N。待复核单列，未提及不进入 N。N=0 显示暂无证据；N<20 显示样本不足，20 是项目展示阈值，不是统计显著性的保证。

默认使用“已复核结果优先，否则使用指定模型版本预测”的有效视图，界面同时显示人工复核比例和版本。另提供纯模型结果视图，算法评估只使用原始模型预测。

验收：用可人工计算的小样本核对计数、分母、复核更新、空数据与重复评论影响。

### FR-07 产品对比与需求预设

允许比较 2～3 款产品，展示相同维度的评价分布、样本数、原文和证据覆盖情况。预设：通勤重点降噪/舒适度，游戏重点延迟/音质，长时间佩戴重点舒适度/续航；用户可调整关注维度。

首版不生成“最佳耳机”总排名，也不将缺失维度填零。解释采用模板，例如“该产品降噪方面有 N 条已判定评论，其中正面占比 X%，请查看代表评论”。预设表达用户需求，不宣称从每条评论推断出了使用场景。

验收：产品选择数量限制正确；同维度口径一致；不足样本与缺失数据清楚显示；每项比较可追溯原文。

### FR-08 导出与可复现信息

管理员导出筛选后的 CSV，包含评论、方面、情感、证据、模型版本和复核标记。公式样式字段须转义，避免表格软件误执行。导出产品汇总时包含分母、统计口径和数据版本。

验收：导出行与筛选结果一致；中文可读；模型和复核来源明确。

### P1 增强项

- 评论明确出现“地铁、通勤、游戏”等词时提取场景标签，未出现时保持未知。
- 接入经过中文耳机领域验证的 ONNX 预训练模型，对照基线评估。
- 错误案例分析页面、更多筛选项和可打印画像。

先通过 P0 验收再开展 P1；深度学习和外部大模型 API 均不作为首版可运行的前提。

## 4. NLP 方案与数据计划

### 4.1 任务定义

本项目是固定方面类别识别与方面情感分类，配合规则式证据定位。不是开放领域命名实体识别，也不承诺抽取所有任意方面词。方面级任务的定义参考 SemEval-2014 Task 4，中文耳机领域需另行标注评估。

推荐流水线：原文保留 → 分句/转折切分 → 方面及别名匹配 → 方面相关局部上下文构造 → 情感分类 → 同方面意见汇总 → 原文证据校验 → 结果入库。

分句和否定处理不能仅用单字子串匹配。例如“不错”不能因含“不”就判为负面。“音质好但续航差”不能整句给两个方面同一个标签。若多个方面共享片段且无法可靠关联，转为待复核。

### 4.2 模型与实现路线

基线 A：方面词典 + 情感词典 + 否定/转折规则，完全本地、可解释，主要用于实验对照。

主方案 B：相同方面定位器 + 中文字符 n-gram 计数特征 + 多项式朴素贝叶斯情感分类器。输入是方面相关局部上下文及方面标记，训练标签为正面、负面、中性；混合由同一评论同一方面的多个局部意见汇总产生。不是将整条评论情感复制到各方面。

采用字符特征减少中文分词安装依赖。词表、特征选择、平滑参数只能依据训练集/验证集确定。Naive Bayes 学习的是频数特征，不能将其描述为已经实现的 TF-IDF+SVM。可使用 ml-naivebayes，并通过 TS 适配层封装；若其兼容性或模型序列化不满足需求，再用 TS 实现明确的计数、平滑和对数概率算法，并配公式示例测试。

训练、推理、评估脚本均使用 TypeScript/Node.js。输出模型文件、词表、标签映射、版本、参数、数据划分清单、校验和和评估 JSON。

模型分数未经验证校准不能展示为“正确概率”。首版主要显示处理状态；若采用拒判阈值，阈值只能在验证集选定，并报告覆盖率与拒判情况。

增强 C：通过 Transformers.js 在 Node.js 运行适用的 ONNX 模型。官方教程证明 Node 推理可行，但模型仍须逐一核实语言、任务、许可证、标签及 CPU 性能；整句情感模型不是天然的方面模型。该库的推理能力也不能写成“在 TS 中完成 BERT 微调”。不预先承诺某个未经验证的模型。

主方案能处理领域内常见明确表述；隐含方面、反讽、跨句指代和复杂比较是已知限制，需以错误案例展示。

### 4.3 数据获得与标注

目标收集 1,500 条去重的真实中文耳机评论，覆盖 3～5 款型号；这是采集目标，当前尚未取得或确认授权。

优先使用授权公开数据或经允许的人工整理/导出数据。记录来源、日期、使用条件、产品和处理方式。通用中文情感语料可帮助验证流程，但只有整句情感标签的数据不能直接当作耳机方面级真值。

另建明确标识的 30～50 条合成边界示例，用于 UI 演示与规则测试，不计入真实效果主结果。若无法获取真实数据，明确将结果限定为教学样例验证，并调整报告结论；不能用合成样例伪装领域性能。

标注层次：评论涉及的方面集合、方面相关证据片段、片段情感、评论层同方面汇总情感、是否含糊。未涉及方面单独编码。

先用 100～200 条试标，修改规范后冻结标签定义。三人共同标注，至少 20% 双人独立标注，冻结测试集全部双人独立复核，由第三人仲裁；报告一致率/情感 Cohen's kappa 和分歧类型。测试标注不得根据模型预测改写。

去重及近重复分组后按评论组划分，目标训练/验证/测试 = 60%/20%/20%；约 900/300/300 条。来自同一评论的各方面片段必须处于同一划分；模板、追评和近重复尽量同组。分组约束优先于精确比例，实际数量写入清单。

报告各方面/情感类别样本量；少样本类别不能只凭总体准确率声称有效。跨型号表现作为分型号诊断，不将随机评论划分结果描述成对未见型号的泛化能力。

### 4.4 早期可行性检查

首个里程碑必须获得可用来源、完成试标并跑通两种基线。若数据量、标签一致性或局部情感效果不足，先补充数据和修订规则/特征，减少增强功能。调整类别或验收目标必须记录变更，不能看过测试结果后反复修改测试口径。

## 5. 技术栈与设计框架

### 5.1 推荐技术栈

- 前端：Vue 3 + TypeScript + Vite + Vue Router + Pinia，Element Plus 用于管理表单，ECharts 用于评价分布。
- 后端：Node.js 稳定 LTS + NestJS + TypeScript，REST API、参数校验、鉴权和 OpenAPI 文档。
- 数据库：SQLite + Prisma，适合本地演示、方便携带和重建数据。
- NLP：TS 独立包，规则与字符特征分类；Node Worker 执行批次处理。
- 测试：Vitest 验证共享逻辑与 NLP；后端集成测试验证接口、鉴权和数据库；Playwright 验证核心浏览器流程。
- 工程：pnpm workspace、严格 TS 类型检查、ESLint、锁文件、环境示例和版本记录。

选择依据：前后端统一语言，模块职责利于三人分工；普通电脑可以完成传统模型训练；SQLite 减少答辩环境配置。数据库后续迁移到 PostgreSQL 需要检查类型与迁移脚本，不能承诺只改连接串即可。

实施前验证稳定版本组合，不采用实验性框架版本。首版不要求 Docker、Redis 或外部付费 API。

### 5.2 架构与模块

浏览器通过 REST 请求 NestJS；NestJS 完成鉴权、校验、业务编排及 Prisma 存取；批次分析交给 Worker 调用 NLP 包，结果分批回写数据库。前端轮询任务状态。静态页面和 API 可由同一部署入口提供。

模块：Auth、Products、Imports、Reviews、AnalysisJobs、Nlp、Corrections、Statistics、Comparison、Exports。统计模块依赖有效结果视图，不自行重新分类文本；前端不维护另一套分母算法。

持久化任务采用单实例 Worker、有限重试和评论级幂等写入。对模型版本及评论建立唯一分析标识；重跑复用或产生明确新版本，不重复累加统计。保存失败原因、进度和时间。

### 5.3 数据模型

- Product：型号、名称、说明。
- ImportBatch：来源、文件指纹、导入/拒绝/重复数量、创建者和状态。
- Review：产品、外部 ID、原文、标准化指纹、可选日期及来源。
- ModelVersion：算法、词表与模型文件校验和、标签定义、参数、训练数据版本。
- AnalysisJob：批次、模型版本、状态、完成数量、失败原因及时间。
- AspectPrediction：评论、模型版本、方面、情感、状态；证据可为关联记录或受校验的 JSON。
- EvidenceSpan：预测 ID、UTF-16 起止索引、证据原文、局部情感。
- Correction：预测 ID、修订结果、证据、管理员、理由、时间和版本。
- AdminUser：管理员凭据哈希和角色，不保存明文密码。

详细设计需补全实体关系、主外键、唯一约束、索引、删除策略、字段可空规则及更新事务。评价汇总以选定版本和复核视图计算，不将不同版本结果混用。

### 5.4 接口契约

接口族包括：管理员登录、产品读取/管理、导入预览/提交、评论筛选、分析任务创建/状态、单条体验、纠正结果、产品统计、对比查询与 CSV 导出。

开发前在 packages/contracts 统一方面枚举、情感枚举、任务状态、分页、证据索引和错误结构。API 不信任前端校验；所有写入接口执行后端鉴权与参数校验。

创建批次分析返回任务 ID，不等待整批完成。模型未加载、任务失败、无数据、超限和无权限各有稳定错误码及可理解提示。

### 5.5 安全与运行约束

仅允许规定格式/大小的上传；上传名不直接作为服务器路径；评论按普通文本渲染，防止 HTML 注入；限制登录尝试与单条分析请求。配置放环境变量，仓库提供示例，不提交凭据。首版绑定本机演示，若以后公开部署，再增加 HTTPS、部署鉴权与运行防护验收。

备份数据库和模型文件。演示前预装依赖与本地模型，核心流程不依赖现场网络。启动脚本须验证数据库迁移、模型存在和健康状态。

## 6. 非功能要求与验收指标

下列数字是初始验收候选与算法目标，不是已有结果。先在试标里程碑验证可行性并确定基线；修改时记录理由。性能必须记录 CPU、内存、操作系统、Node 版本、模型、数据量、请求数、是否预热。

### 6.1 功能与可靠性硬要求

- 所有 P0 需求均有对应验收用例；P0 用例通过率 100%，未解决的阻断/严重缺陷为 0。
- 所有展示证据片段与原文偏移一致；测试中不得出现生成的“原文”。
- 相同数据重复导入/任务重试不重复计数，人工纠正后汇总与明细一致。
- 未授权写操作全部拒绝，异常上传不污染已提交数据。
- 重启后已完成结果仍可访问，未完成任务有明确状态。
- 锁定模型、输入、配置后重复预测标签一致。

### 6.2 NLP 效果目标

- 方面类别识别 micro-F1 目标 ≥0.80，另报告 macro-F1 和每方面指标。
- 在人工真值方面及证据上下文输入下，三类情感 macro-F1 目标 ≥0.75；这是独立分类阶段指标。
- 端到端“评论—方面—情感”集合 micro-F1 目标 ≥0.70。该指标同时计算错误方面、错误情感和漏检；混合情感作为独立汇总标签参与评估。
- 展示证据定位 token/字符重叠 F1 或人工相关性结果，并区分“索引正确”与“语义相关”。索引正确不能证明情感判断正确。
- 如有拒判，报告覆盖率；待复核/漏识别在端到端评价中不能被删去来提高分数。
- 两种方法在相同冻结测试集评估，报告混淆矩阵、类别支持数、分型号结果和至少 10 个有代表性的错误案例。

若目标未达成，记录实际结果、问题原因和改进过程；不能把目标值直接填入报告，也不能仅凭精选演示判断算法达标。

### 6.3 性能与可用性目标

暂定验收环境为至少四核 CPU、8 GB 内存、无 GPU，数据库约 5,000 条评论；最终填写真实设备规格。

- 本地已构建页面首次可操作时间目标 ≤3 秒，记录多次测试分布。
- 普通查询 API 在 10 个并发浏览者下 p95 ≤500 ms；单条文本分析在已加载传统模型时 p95 ≤1 秒。
- 1,000 条、每条不超过 200 字的基线批次分析目标 ≤60 秒；独立记录导入、分析、统计耗时，失败行另计。
- 页面支持 1366×768 和 1920×1080，无核心按钮遮挡；图表有文字计数，情感不只靠颜色区分。
- 冷启动与预热分别记录，不用预热结果替代首次加载体验；增强模型单独测量，不沿用传统模型耗时结论。

## 7. 测试与需求追踪

### 7.1 测试层次

单元测试：切句、否定与转折、多方面归属、证据偏移、汇总分母、去重、模型保存/加载一致性。覆盖“没有降噪”“降噪不差”“音质好但续航短”、emoji 及同方面正负冲突。

集成测试：上传校验、登录鉴权、任务状态、Worker 结果入库、幂等重试、纠正事务、统计一致性和导出。

端到端测试：登录 → 导入预览 → 提交 → 分析 → 查看证据 → 纠正 → 画像更新 → 产品对比 → 导出；另覆盖无数据与失败任务。

算法评估：冻结独立测试集，一次版本化评估；测试集参与调参后须声明污染并更换独立评估集。

### 7.2 追踪示例

- FR-02 → Imports/Reviews → 导入预览与提交接口 → TC-IMPORT-01/02 → 导入日志、错误行截图。
- FR-04 → Nlp/AspectPrediction → 单条体验与批次接口 → TC-NLP-01、冻结测试集评估 → 高亮截图、评估 JSON。
- FR-06 → Statistics → 产品画像接口 → TC-STATS-01/02 → 人工计数样本与结果截图。
- FR-07 → Comparison → 对比接口 → TC-COMPARE-01/02 → 完整证据/缺失证据两组展示。

实施时扩展到每一项 P0，确保没有需求仅写在报告中而缺少测试或实现证据。

## 8. 三人分工与里程碑

### 8.1 分工

成员 A：前端与体验。负责页面、路由、状态管理、图表、原文高亮、浏览器验收；主写系统展示与界面设计。

成员 B：后端与数据。负责数据库、接口、鉴权、导入、任务调度、复核、统计、导出与运行脚本；主写总体设计、数据库/接口详细设计及后端实现。

成员 C：NLP 与实验。负责标注规范、方面词典、规则基线、训练/推理/评估脚本、模型版本与错误分析；主写算法详细设计、算法实现与效果测试。

三人共同完成需求分析、数据标注、接口评审、交叉测试和最终报告校对。每人需掌握完整演示流程，成员 C 不承担全部标注，成员 A 不承担全部文档。分工是团队安排，不是本轮启用自动子代理开发。

### 8.2 暂定四周节奏

第 1 周：明确需求和标注规范；验证数据来源；完成试标和两种方法原型；确定 API 契约、数据库草图和页面线框。出口：需求基线 v1、可行性结论、一个真实文本分析样例。数据或算法存在问题时在此调整，不能等界面完成才发现。

第 2 周：完成产品、导入、任务、NLP 入库和评论查看；扩大标注。出口：一批真实评论可完成“导入—分析—原文查看”，阶段性设计文档与集成测试。

第 3 周：完成复核、画像、对比、导出；冻结模型/测试划分，开展端到端和性能测试。出口：P0 功能完整，真实评估结果与错误案例，严重缺陷列表。

第 4 周：修复缺陷、验证重建与离线演示、补齐追踪、渲染最终报告并采集截图，录制演示。出口：可运行发布包、报告、测试证据、演示材料和版本清单。

工作量按三人兼职投入估计；不是确定交付日期。若期限不足，优先删减 P1，保留核心闭环、数据说明、独立评价和软件工程文档。
