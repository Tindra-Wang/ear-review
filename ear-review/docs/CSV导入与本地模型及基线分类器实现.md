# CSV 导入流程、本地模型调用接口与基线分类器实现

本文解释耳机评论系统中这三部分怎样连接起来，依据 2026-10-12 查看的源码编写。当前代码已经增加 Ollama 本地文本模型分支，因此需要区分“本地文本模型推理”与“朴素贝叶斯基线”，不能将两者混称为同一种分析手段。

## 1. 整体流程

```text
CSV 文件 / 单条评论
        ↓
前端读取、选择字段与分析方式
        ↓
NestJS：校验、鉴权、导入或单条分析接口
        ↓
分析路径二选一
  A. 本地 Ollama 文本模型：结构化语义分析
  B. 本地 TypeScript 基线：方面词典 + MNB + 情感规则
        ↓
返回方面、情感、处理状态与真实原文证据
        ↓
前端展示；批次结果保存到 SQLite，再计算画像与对比
```

单条体验不写入产品统计。CSV 批次经入库、创建任务和后台分析后，结果才参与产品画像。上传 CSV、执行推理和训练模型是三个不同动作。

## 2. CSV 导入流程

### 2.1 前端读取文件

前端使用浏览器文件 API 读取用户选择的 CSV，支持选择 UTF-8 或 GB18030/GBK 编码。原始列名不必和系统字段完全一致，可以先识别列，再由用户确认映射。

例子：

```csv
productId,reviewId,text,source
my-earphone,r001,"音质很好，但戴久了耳朵疼。",教学格式示例
my-earphone,r002,"通话很清晰，不过续航太短。",教学格式示例
```

上面的文本只是说明格式的合成样例。真实导入需填写真实来源和使用说明。

当前实现允许只有评论正文列：评论编号缺失时根据正文指纹生成；产品编号缺失时使用用户选择的产品或集合。正式导入应核对数据的商品归属，不得把其他产品评论冒充所选耳机评论。

### 2.2 识别与映射字段

前端调用 `POST /api/imports/columns`。后端的 `parseImport()` 使用 `csv-parse`：

1. 检查文件大小、引号、分隔符、列数和表头。
2. 将每条记录转换为“原列名 → 单元格值”的对象。
3. 按别名推断映射，例如 `review`、`review_body`、`评论内容`可以作为正文列候选。
4. 返回表头、候选映射、前三条样本和总行数。

如果有多个候选列，不能确定唯一映射，需要用户选择。`mapImport()` 将原始列转换为系统的 `text、reviewId、productId、source`，并拒绝不存在的列或同一列映射到多个字段。

### 2.3 校验并预览

前端通过 `POST /api/imports/preview` 发送 CSV、映射、来源说明、教学标记及可选统一产品 ID。该接口要求管理员登录。

当前导入边界为单文件不超过 5 MB、最多 5,000 行、每条最多 5,000 个 Unicode 字符。还需检查正文为空、编号超长、产品不存在等问题；超长文本报错，不静默截断。

去重使用两种条件：

- 产品 ID 与评论 ID 相同。
- 产品 ID 与标准化正文指纹相同。

正文指纹的计算方式是 NFKC 规范化、去除空白、小写化后计算 SHA-256。这个标准化结果用于去重，数据库仍保存原文。

后端同时检查本批次内与数据库中的重复记录，返回有效数、错误数、重复数、行号和错误原因，并生成有效期 15 分钟的预览标识。此阶段不写入正式评论表。

### 2.4 确认提交

用户确认后调用 `POST /api/imports/commit`，提交预览标识。服务器检查管理员身份、标识有效性和是否存在可导入记录，再调用 `Store.importRows()`。

该方法在 SQLite 事务中保存批次、有效非重复评论和校验概要。数据库还设置两组唯一约束，避免再次插入重复评论。发生异常时回滚；提交成功后预览标识失效，重复提交被拒绝。

### 2.5 创建分析任务

前端在提交成功后调用 `POST /api/jobs`，传入批次 ID 与分析模式。后端创建持久化任务，并由 `worker_threads` 执行批量计算。

Worker 按用户选择调用语义模型或基线，逐条返回结果与错误；主线程保存预测、更新进度，并记录模型版本。基线最多处理 1,000 字，导入的长评论需要选择语义模型，否则记录明确错误，不截断原文。

保存后才能根据评论结果计算画像。**CSV 导入不会自动修改任何模型参数。**

- [字段解析与映射](../apps/api/src/importer.ts)：`parseImport()`、`mapImport()`。

## 3. 本地模型调用接口

### 3.1 浏览器只调用本项目后端

单条评论通过 `POST /api/analyze` 分析。例如调用基线：

```json
{
  "text": "音质很好，但戴久了耳朵疼。",
  "mode": "hybrid"
}
```

服务器验证输入后，依据 `mode` 分流：

- `hybrid`：调用本地 TypeScript `analyze()`，结合 MNB 与情感规则。
- `rules`：规则对照口径，没有明确规则的表达不作为已判定意见。
- `semantic`：调用 `analyzeSemantic()`，请求独立运行的本地 Ollama。

基线接口允许最多 1,000 字，语义接口最多 5,000 字。配置、服务连接或推理失败会明确返回错误，不把失败伪装成成功分析。

### 3.2 TypeScript 基线如何运行

服务读取 `MODEL_PATH`，默认是项目内的 `data/model.json`。文件存在时校验并加载词表、类别频数和版本；不存在时使用内置教学语料构造模型。

基线全部计算在 Node.js CPU 中执行，不需要 Ollama，也不请求外部大模型。加载 JSON 模型和运行预测都不等于重新训练。

### 3.3 Ollama 文本模型如何调用

`semantic.ts` 默认连接 `http://127.0.0.1:11434`，默认模型标签为 `qwen3:4b`，也可以通过 `OLLAMA_URL` 与 `OLLAMA_MODEL` 配置。

调用过程为：

1. 通过 `/api/tags` 检查本地服务及目标模型标签。
2. 将评论与固定方面分析提示词发送到 `/api/chat`。
3. 使用 JSON schema 约束方面、情感、证据等输出字段。
4. 检查响应结构，并核对证据确实属于输入原文。
5. 返回结构化意见、模型版本、耗时及推理统计。

TypeScript 在这里负责组织请求和验证结果，参数矩阵计算由 Ollama 执行。Web 项目集成了这条调用路径，并不自动证明机器上已安装 Ollama、下载权重或完成模型运行验证，应以实际健康检查与推理记录为准。

当前输入只有文字，这是文本模型推理，不是图像、音频和文字联合的多模态分析。项目也没有在此接口中训练或微调 Qwen3。

## 4. 基线分类器如何训练

### 4.1 带标签训练数据

有监督训练输入与分析导入 CSV 不同：

```csv
aspect,text,label
sound,音质很好,positive
comfort,戴久了耳朵疼,negative
battery,支持无线充电,neutral
```

`aspect` 是评价方面，`text` 是相关局部片段，`label` 是确认的情感真值。商品总评分不能替代每个方面的标签。

默认训练使用开发时编写的 126 条教学合成样例：六方面分别包含七条正面、七条负面、七条中性。它们不是已经采集的真实消费者评论。

### 4.2 中文文字转换为特征

`features()` 将输入小写化并去掉空白和部分标点，统计连续的一字、二字、三字片段频次。方面标记也被拼接进输入。

以“音质清晰”为例，省略方面标记时：

- 一字片段：音、质、清、晰。
- 二字片段：音质、质清、清晰。
- 三字片段：音质清、质清晰。

这些频数构成模型特征。当前基线没有使用 TF-IDF、词向量、中文分词库或 BERT。

### 4.3 多项式朴素贝叶斯学习

`train()` 按正面、负面、中性三类统计文档数和特征频数，建立训练词表。它是一个共享分类器，方面标记参与特征；不是六个独立分类器。

设总训练文档数为 `N`，类别文档数为 `Nc`，类别特征总频数为 `Tc`，词表为 `V`，则当前代码采用加一平滑：

```text
P(c) = (Nc + 1) / (N + 3)
P(f | c) = (count(f, c) + 1) / (Tc + |V|)
score(c) = log P(c) + Σ count(f, x) × log P(f | c)
```

预测时只计算训练词表内特征，最高分的类别是情感候选。训练是频数统计与概率估计，没有反向传播、训练 epoch 或 GPU 梯度计算。

### 4.4 保存与重新训练

在项目目录执行：

```powershell
npm run train
```

模型写入 `data/model.json`，保存词表、三类计数、样例数、来源类型和数据哈希版本。准备好真实标注训练划分后可以另行导出：

```powershell
npm run train -- --data data/authorized-train.csv --kind "授权真实训练集" --output data/models/real-v1.json
```

上述输入文件需要先准备；设置 `MODEL_PATH` 指向新模型并重启后端才会使用它。验证和测试样例不能混入训练文件。

对应代码：[特征、训练与预测](../packages/nlp/model.ts)、[训练入口](../scripts/train.ts)、[教学训练样例](../packages/nlp/training-data.ts)。

## 5. 基线怎样产生方面级分析结果

对于“音质很好，但戴久了耳朵疼”：

1. `splitClauses()` 按标点和转折词切分，同时保留原文偏移。
2. `ASPECT_PATTERNS` 的词典正则识别 sound 和 comfort。当前方面识别主要依靠规则，没有训练出方面识别神经网络。
3. `predict()` 对各方面的局部片段产生三类情感候选。
4. 混合模式中明确的情感规则优先，例如“很好”为正面、“耳朵疼”为负面；规则没有覆盖时使用模型候选。
5. 模型分差较低或多个方面共享意见且难以归属时，标记待复核。当前分差阈值 3 是启发式，不是已校准的正确概率。
6. 同方面的不同片段同时正负时汇总为 mixed；mixed 是后处理结果，不是 MNB 的第四个训练类别。
7. 返回对应原文片段及 UTF-16 左闭右开索引，前端据此高亮。

该例得到“音质正面、舒适度负面”。其他方面未提及，不补成中性。规则对照内部仍计算模型候选，但无明确规则时保持待复核，不把候选当作规则已确认结果。

对应代码：[基线分析流程](../packages/nlp/index.ts)、[原文高亮组件](../apps/web/src/components/EvidenceText.vue)。

## 6. 实现边界与报告口径

- CSV 导入是数据接入；推理是用现有模型分析；训练是根据标注样例估计参数，不能混为一谈。
- 人工复核保存为修订记录，不会自动重训练 MNB，更不会自动微调 Qwen3。
- MNB 基线教学检查成绩不能代表真实领域效果，也不能当作 Ollama 文本模型成绩。
- 规则、MNB 与文本模型都可能误判，原文真实性校验不能证明情感判断正确。
- 实际权重部署、MNB重训和Qwen3推理对照已经执行；代码调用关系见本文，运行结果和错误见[模型对照实验报告](模型对照实验报告.md)。
