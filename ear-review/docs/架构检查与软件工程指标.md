# 模块耦合、内聚与 NLP 工程检查报告

检查日期：2026-10-14。对象：当前工作区中的实际实现，不是规划中的目标架构。结论：已有分层和模块化基础，NLP 核心模块职责较集中，但前端编排、API 业务编排与存储层尚未全面达到低耦合、高内聚。本次只检查并绘图，不修改业务行为或训练权重。

## 1. 检查方法与标准口径

采用静态代码检查、TypeScript AST 依赖扫描、实际 API/数据库链路追踪，以及现有实验与测试证据核对。质量维度参考 [ISO/IEC 25010:2023 产品质量模型](https://www.iso.org/standard/78176.html)：模块化、可修改性、可测试性、功能正确性、可靠性与性能等。该标准不是“文件小于多少行”或“F1 必须达到多少”的评分规则；下文工程门槛是本项目建议的验收目标，不能称为 ISO 认证。

NLP 任务采用方面级情感分析，方向依据 [SemEval-2014 Task 4](https://aclanthology.org/S14-2004/)，结合耳机领域固定六方面构建本项目的输出契约。这里不是复现该公开任务的完整数据集或榜单。

可复现检查命令：在 ear-review 目录执行 `node scripts/audit-architecture.mjs`。原始结果见 [架构检查指标.json](架构图/架构检查指标.json)。扫描生产 apps/packages/scripts 中的 TS 与 Vue script；排除测试、构建产物与 data 语料文件。fan-in/fan-out 是项目内源文件直接运行时依赖数量，type-only 另列，并补入 Worker URL 依赖。它不是完整函数调用图，不是圈复杂度，也不是 LCOM 内聚度。

## 2. 实测结构指标

32 个生产源文件，52 条项目内运行时依赖边，未发现此扫描范围内的运行时循环依赖。没有循环依赖只能说明依赖方向较清晰，不能证明高内聚。

ApiController 包含 30 个 HTTP 端点、33 个方法，项目内 fan-out 为 9，并包含 39 处符合数据库调用语法的调用。App.vue 有 46 处 ref 调用，项目内 fan-out 为 8；文件约 32.5 KB。Store 约 11.1 KB，包含 14 个方法。许多模板和方法被压缩在一行，不能用物理行数低来证明代码简单。

NLP index.ts fan-out 为 2；semantic.ts 为 1；model.ts 为 1。它们均未直接依赖 Vue、Controller、Store 或 SQLite。contracts 为共享 DTO 与领域枚举，前后端通过 HTTP JSON 交互，不共享数据库连接。

## 3. 当前模块是否低耦合、高内聚

### 前端：组件相对集中，顶层编排职责过多

ProductOverview、AnalysisTasks、PlatformCollection、ReviewList、ImportMapping 等组件有明确展示或操作职责，适合单独维护。但 App.vue 同时管理认证、产品、CSV 上传和预览、批次任务、画像过滤、对比、单条分析与多个定时刷新。增加一条业务路线仍会改到同一文件，三人并行开发容易冲突。

建议将各路由内容拆成 OverviewPage、ImportPage、CollectionPage、ProfilePage、ComparePage；将 CSV 导入与任务轮询分别放入 composable。保留 api.ts 作为 HTTP 适配层，页面不能直接调用模型服务或数据库。该拆分是建议，目前没有假装已完成。

### API Controller：当前最明显的内聚问题

controller.ts 不只接收请求，还持有预览缓存、采集锁、浏览器运行集合、Worker 生命周期、任务状态转换、评论汇总与导出逻辑，并直接执行多条 SQL。它的职责横跨多个变化原因，新增平台、改变数据库或替换任务执行器会影响同一类。

建议按业务域拆成 CollectionService、ImportService、AnalysisJobService、ProductQueryService、CorrectionService，并由相应 Controller 调用；数据库查询通过 Repository 的领域方法封装。不能为了降低计数而只把巨大文件机械切开，应让每个模块负责一个变化原因。

### Store：存储隔离存在，依赖方向尚不够纯粹

Store 对数据库的连接、事务、查询做了集中封装，但对外公开 one/all/run，因此 Controller 和 Auth 仍能依赖表名与 SQL。Store 同时负责 schema 迁移、重启恢复、样例生成、调用基线分析、人工复核合并与方面统计。样例初始化使存储模块反向依赖 NLP 运行时及 data/demo.ts。

建议将建表迁移、样例初始化与启动恢复移至独立 bootstrap/migration；将方面统计与复核有效视图抽成查询服务或纯函数；将数据访问分成 Product/Review/Job/Collection Repository。SQLite 可以继续保留，不需要为课程规模上微服务。

### NLP：边界较好，替换模型仍需触及编排

model.ts 负责 MNB 特征、训练、模型加载与预测；index.ts 负责分句、方面识别、规则及证据聚合；semantic.ts 负责 Ollama 请求、提示词、结构化输出与校验。数据输入与 Analysis 输出契约稳定，算法可以脱离 Web 测试，这是当前最接近高内聚的部分。

但 semantic.ts 集中了服务探测、推理、Prompt、恢复和校验；配置通过 process.env 读取。Worker 和 Controller 都直接判断 semantic 并依赖具体函数/版本前缀，尚无可注入的 AnalysisEngine 接口。建议引入统一 `analyze(text): Promise<Analysis>` 与 version/health 的模型适配器；保持语义错误明确失败，不静默转成规则结果。

### 采集：适配器隔离较好，状态编排仍在 Controller

公开端点采集与 Chrome/CDP 采集是独立文件；浏览器采集只返回评论行与采集进度，不直接写 reviews。采集 CSV 需用户预览并确认导入，这一边界是合理的。站点 DOM 变化主要影响 browser-collector.ts，平台访问限制不能靠架构宣称已经解决。

建议将浏览器会话及 collections 状态迁移收敛到采集服务，按平台建立可单独测试的页面解析器。人工登录或验证是正常输入条件，不属于自动翻页失败，也不能把只能取到部分评论标为取得全部目标数量。

## 4. 优先级与具体问题

**P1：统计查询的扩展性。** Store.reviews() 先获取全部 ID，再逐条调用 review()，每条再查 predictions 与 corrections；属于 N+1 查询。stats、summary、compare 会重复拉取和聚合。几百条可用不代表 5000 条仍达标。建议联表/批量加载、数据库分页，汇总复用同一份有效视图，先测耗时再决定缓存。

**P1：重试与结果版本复现不足。** 当前分析重试是新建任务后重跑整个批次，并非只跑失败评论。predictions 以 review_id/version 更新，同版本历史输出会被后续结果替换；保留旧 job 记录并不等于保留所有逐次输出。MNB version 主要由训练数据哈希决定，未包含规则代码版本；语义版本包含标签和 Prompt 版本，但不是完整的权重摘要。建议记录推理 run_id、权重 digest、代码/规则/Prompt 哈希与配置，保留逐次输出，重试按失败集合选择。图中已如实标明当前行为。

**P1：当前真实评论 NLP 金标准缺失。** 结构化输出通过、原文证据存在和任务完成，不等于方面/情感识别正确；absa-v4 缺少独立标注的真实评论测试结果。

**P2：业务与持久化耦合。** Controller 直接 SQL，Store 包含领域统计和样例模型分析，Auth 依赖具体 Store。建议以领域接口隔离；在完成接口迁移前先保持已通过的行为测试。

**P2：共享前端状态与契约分散。** App.vue 的多页面状态集中，DataBatch 类型目前导出自展示组件。建议把 API DTO 放到 packages/contracts，将按业务使用的状态局部化；不是要求引入全局状态库。

## 5. NLP 两条路线与训练边界

路线 A：Qwen3:4b 本地预训练文本模型，经 Ollama /api/chat 推理。历史权重证据为 GGUF Q4_K_M，4.0B，2497293931 bytes，位于 D:\NLP\大作业\模型权重；历史设备记录为 RTX 5060 Laptop GPU。CPU 上运行 TypeScript 编排，GPU 执行模型计算，实际分配应以当次 Ollama /api/ps 为准。模型没有在本项目微调或从零训练。[Qwen 官方说明](https://qwenlm.github.io/blog/qwen3/)提供模型背景；本项目具体参数以代码和本地实验记录为准。

语义流程：完整文本 → 保留原文的编号片段 → Prompt 与 JSON Schema → Qwen 选择方面/情感/表达类型/强度/证据编号 → 服务端恢复原文证据与偏移 → 校验 → 统一 Analysis。think=false、temperature=0、num_ctx=16384、num_predict=4096；对输出不合格最多再次请求一次，总时限 180 秒。语义失效会写入 job_errors，不转成规则假装成功。不调用多模态模型。

路线 B：126 条人工合成有标签训练样例，正面/负面/中性各 42 条 → 字符 1/2/3-gram → 累计类别文档数与词频 → add-one 平滑的多项式朴素贝叶斯 → 参数 JSON。历史词表 1172，参数文件 51217 bytes，保存到模型权重/classifiers/mnb-8a862b69.json；基线为 Node.js/TypeScript CPU 训练。它采用统计计数，不存在神经网络的 epoch、反向传播或训练 loss 曲线。

Web 的基线是方面词典 + 分句 + MNB 情感候选 + 领域规则 + 证据合并；混合情感来自同方面正负证据聚合，不是 MNB 的第四个直接训练类别。对照里的 pure MNB 也仍使用方面词典，只是禁用情感规则，所以其方面 F1 不能当成 MNB 学会了方面识别的证据。

评论导入 CSV 只要求正文、归属与来源。模型训练 CSV 则需要 aspect,text,label，是另一条显式训练流程。执行 `npm run train -- --data 标注训练集.csv --kind 授权真实训练集 --output 模型参数.json` 后还需通过 MODEL_PATH 选择参数并重启相应服务。`npm run model:pull` 是下载 Qwen 预训练权重，不是训练。未标注评论不会自动成为有监督训练数据；人工复核目前也不会自动回流训练。

## 6. 指标、已测结果与建议验收

### 软件工程指标

建议门槛：项目内部禁止循环依赖；NLP 模块不依赖 Web/API/DB；展示组件不执行 SQL；业务 Controller 不直接操作 Repository 底层 SQL；每个分析任务的成功、失败和未处理条数可追溯；导入同一 CSV 不重复计入；失败保留此前成功结果；证据偏移合法率 100%；无效输入不得静默截断。

当前证据：扫描范围循环依赖为 0，NLP 到 Web/API/DB 运行时依赖为 0；Controller 直接 SQL 门槛未满足。最近一次完整验证为 47 项单元测试、13 项端到端测试通过，涵盖 CSV 中文列映射、鉴权、去重、任务、复核、证据与浏览器受控页面；这不是代码覆盖率 100%，也不是所有电商实站均能采集。

性能建议验收环境固定为本机硬件，分别测 100、1000、5000 条评论下的导入、分页、统计接口 P50/P95、峰值内存与批量吞吐。可先以分页/汇总 P95 ≤ 1 秒、1000 条导入 ≤ 5 秒为项目目标；当前未实测该规模性能，不宣称达标。语义模型允许单条总上限 180 秒，单 Worker 防止批次并发把本地显存耗尽；批次耗时与评论长短及模型生成量有关，不承诺固定速度。

### NLP 质量与运行指标

固定口径：方面 micro P/R/F1；方面-情感对 micro-F1 与按有支持类别计算的 macro-F1；逐类支持量与分数；完全匹配率；待复核率；请求失败率；证据子串合法率；成功调用函数耗时 P50/P95。失败样例计入质量统计，不能通过过滤失败抬高结果；耗时分位数当前只包含成功调用并不包含入库/网页展示。

历史 42 条人工对照样例（absa-v2，非真实买家数据）：

- MNB：方面 F1 98.04%，方面-情感对 micro-F1 78.43%，macro-F1 77.01%；失败 0/42；P95 0.46 ms。
- MNB + 规则：方面 F1 98.04%，方面-情感对 micro-F1 79.55%，macro-F1 75.39%；待复核方面评价 27.45%；P95 0.36 ms。
- Qwen3：方面 F1 85.39%，方面-情感对 micro-F1 74.16%，macro-F1 55.46%；失败 3/42；成功调用 P95 2516 ms。

这些指标可从 [模型对照结果.json](实验结果/模型对照结果.json)复算。该小样本上 Qwen 没有优于基线，不能因为“大模型”就宣称更准确；选择它是为扩展复杂语义处理能力，但收益必须用真实独立测试证明。历史参数计数训练耗时约 2.03 ms，仅为 train 函数计时，不含启动、读文件与写文件。

建议下一次验收先建立不少于 300 条真实授权评论的独立标注数据；按产品、来源或时间分组切分并在切分前去重，两人独立标注、第三人裁决分歧。冻结测试集，再比较语义、pure MNB、混合基线和规则；单独报告反讽、否定、同方面混合、跨句、未提及及长度分层结果。可设端到端 micro-F1 ≥ 0.80、macro-F1 ≥ 0.75、技术成功率 ≥ 95% 为初始项目目标，但这属于待验收目标，当前 absa-v4 真实数据尚无结果。

## 8. 建议的三人分工与迭代顺序

第一位负责 Vue 路由页、导入交互与可视化；第二位负责 Controller/Service/Repository、SQLite 与任务生命周期；第三位负责采集适配、训练数据与 NLP 评估。共享 contracts 与模型版本字段统一评审。

先冻结已通过的功能测试和数据口径，再提取查询 Repository 与业务服务，随后拆前端路由状态，最后完善真实标注与模型版本溯源。每步都以相同导入/分析/复核/展示结果验证，不建议一次重写全部系统。验收应检查行为与依赖方向，不按新增文件数量评判低耦合。
