检查日期：2026-10-14。对象：当前工作区中的实际实现，不是规划中的目标架构。结论：已完成保持行为的模块重构，业务状态、HTTP 适配、业务服务、持久化与模型推理的职责已分离。30 个 HTTP 端点保持不变，构建、49 项单元/集成测试及 13 项端到端测试通过；实际数据库的 26 组新旧结果只读比对全部一致。低耦合、高内聚通过依赖方向和职责边界落实，不宣称一个无法测定的“内聚度百分比”。本次未改训练权重、提示词、情感规则或页面交互。

## 1. 检查方法与标准口径

采用静态代码检查、TypeScript AST 依赖扫描、实际 API/数据库链路追踪，以及现有实验与测试证据核对。质量维度参考 [ISO/IEC 25010:2023 产品质量模型](https://www.iso.org/standard/78176.html)：模块化、可修改性、可测试性、功能正确性、可靠性与性能等。该标准不是“文件小于多少行”或“F1 必须达到多少”的评分规则；下文工程门槛是本项目建议的验收目标，不能称为 ISO 认证。

NLP 任务采用方面级情感分析，方向依据 [SemEval-2014 Task 4](https://aclanthology.org/S14-2004/)，结合耳机领域固定六方面构建本项目的输出契约。这里不是复现该公开任务的完整数据集或榜单。

可复现检查命令：在 ear-review 目录执行 `node scripts/audit-architecture.mjs`。原始结果见 [架构检查指标.json](架构图/架构检查指标.json)。扫描生产 apps/packages/scripts 中的 TS 与 Vue script；排除测试、构建产物与 data 语料文件。fan-in/fan-out 是项目内源文件直接运行时依赖数量，type-only 另列，并补入 Worker URL 依赖。它不是完整函数调用图，不是圈复杂度，也不是 LCOM 内聚度。

## 2. 实测结构指标

重构前：32 个生产源文件、52 条项目内运行时依赖边；Controller 30 个端点、39 处 SQL 调用、fan-out 9；App.vue 46 处 ref 声明；无运行时循环依赖。重构前摘要保存于[重构验证结果.json](架构图/重构验证结果.json)。

重构后以[架构检查指标.json](架构图/架构检查指标.json)为准：Controller 仍为 30 个端点，SQL 调用为 0，fan-out 为 2；App.vue 中 ref 声明为 5，其余状态按六个业务 composable 管理；扫描范围内运行时循环依赖及已定义的层间依赖违规均为 0。Store 不再执行 SQL 或调用 NLP，其职责为仓储组合和兼容转发。

App.vue 的 fan-out 从 8 增至 14，因为它显式组装六个业务模块。整个项目依赖边也随模块拆分增多；这不等于耦合恶化，不能单纯以文件数或总边数评判质量。可替换边界、依赖方向和跨模块职责更重要。AST 统计不是完整调用图或 LCOM，类型依赖单列，外部包不计入本地 fan-out。

## 3. 当前模块职责与依赖方向

### 前端：页面组合与业务状态分离

App.vue 保留路由组合、全局反馈、服务状态及启动/轮询，不再包含 CSV 解析映射、导入提交、登录逻辑、复核刷新和对比加载的具体实现。composables/useSingleAnalysis、useProductReviews、useProductComparison、useDataWorkspace、useAuth、useProductManagement 各自管理一个业务场景的状态与操作。

跨场景协调通过参数和回调传入：复核刷新调用对比刷新回调；登录后加载工作台、退出后清理工作台通过回调连接。各 composable 不相互导入，也不依赖展示组件。DataBatch 已移至 packages/contracts，与后端返回契约统一。页面模板、样式、导航、按钮和交互保持原样。

### HTTP 适配与业务服务

ApiController 只负责 30 个路由的参数接收、鉴权、响应头和服务转发；不执行 SQL、不启动 Worker、不创建模型或浏览器实例。application-services.ts 在启动边界组合五个业务服务，通过 Nest 的 SERVICES 注入 Controller。

CollectionService 管理采集会话和状态；ImportService 管理字段识别、校验、预览归属/过期及提交；AnalysisJobService 管理队列、幂等、Worker 生命周期和进度；ProductService 管理查询、对比、复核、导出与产品维护；ModelService 管理模型信息、单条分析及限流。鉴权仍在 HTTP 边界执行，预览归属与复核操作者传给业务服务，不把 Request 对象传进领域逻辑。

### 数据访问与聚合

六个 Repository 按 Product、Review、Batch、Job、Collection、Admin 聚焦数据访问。服务依赖 Pick<Store,...> 的窄能力约束，Auth 只依赖管理员仓储的 get/create，不再依赖整个 Store。SqliteDatabase 管理连接与事务；database-bootstrap 管理建表、迁移及中断状态恢复；application-bootstrap 单独管理首次样例初始化，仓储不导入 NLP 或样例数据。

product-statistics 为纯聚合函数，输入产品与有效评论，输出统计，不访问数据库。summary 复用同一次批量评论读取。ReviewRepository 批量读取最新预测和同版本复核：有效视图恒为 2 次 SELECT，pure 视图 1 次；原来是 1+2N 次和 1+N 次。版本筛选、复核顺序、原模型证据、评论倒序与统计分母均保持。

### NLP 与采集边界

packages/nlp/engines.ts 提供统一 AnalysisEngine 契约：version、maxChars、analyze、readiness；单条与 Worker 经同一入口调用基线或语义模型，历史版本到模型类型的识别集中在该边界。MNB 算法、方面规则、Qwen Prompt/Schema/原文恢复与校验未改；语义失败不会静默降级。接口已定义，但当前仍为本项目两种实现，没有引入插件发现或远程队列。

公开采集和 Chrome/CDP 适配器仍返回评论行及进度，CollectionService 通过采集仓储保存 CSV；正式评论需预览确认导入。自动滚动、翻页、正常登录恢复、商品编号核对、限额与去重行为保留。平台 DOM 变化或访问限制仍可能影响实站采集，架构拆分不代表所有平台采集都能成功。

## 5. NLP 两条路线与训练边界

路线 A：Qwen3:4b 本地预训练文本模型，经 Ollama /api/chat 推理。历史权重证据为 GGUF Q4_K_M，4.0B，2497293931 bytes，位于 D:\NLP\大作业\模型权重；历史设备记录为 RTX 5060 Laptop GPU。CPU 上运行 TypeScript 编排，GPU 执行模型计算，实际分配应以当次 Ollama /api/ps 为准。模型没有在本项目微调或从零训练。[Qwen 官方说明](https://qwenlm.github.io/blog/qwen3/)提供模型背景；本项目具体参数以代码和本地实验记录为准。

语义流程：完整文本 → 保留原文的编号片段 → Prompt 与 JSON Schema → Qwen 选择方面/情感/表达类型/强度/证据编号 → 服务端恢复原文证据与偏移 → 校验 → 统一 Analysis。think=false、temperature=0、num_ctx=16384、num_predict=4096；对输出不合格最多再次请求一次，总时限 180 秒。语义失效会写入 job_errors，不转成规则假装成功。不调用多模态模型。

路线 B：126 条人工合成有标签训练样例，正面/负面/中性各 42 条 → 字符 1/2/3-gram → 累计类别文档数与词频 → add-one 平滑的多项式朴素贝叶斯 → 参数 JSON。历史词表 1172，参数文件 51217 bytes，保存到模型权重/classifiers/mnb-8a862b69.json；基线为 Node.js/TypeScript CPU 训练。它采用统计计数，不存在神经网络的 epoch、反向传播或训练 loss 曲线。

Web 的基线是方面词典 + 分句 + MNB 情感候选 + 领域规则 + 证据合并；混合情感来自同方面正负证据聚合，不是 MNB 的第四个直接训练类别。对照里的 pure MNB 也仍使用方面词典，只是禁用情感规则，所以其方面 F1 不能当成 MNB 学会了方面识别的证据。

评论导入 CSV 只要求正文、归属与来源。模型训练 CSV 则需要 aspect,text,label，是另一条显式训练流程。执行 `npm run train -- --data 标注训练集.csv --kind 授权真实训练集 --output 模型参数.json` 后还需通过 MODEL_PATH 选择参数并重启相应服务。`npm run model:pull` 是下载 Qwen 预训练权重，不是训练。未标注评论不会自动成为有监督训练数据；人工复核目前也不会自动回流训练。

## 6. 指标、已测结果与建议验收

### 软件工程指标

建议门槛：项目内部禁止循环依赖；NLP 模块不依赖 Web/API/DB；展示组件不执行 SQL；业务 Controller 不直接操作 Repository 底层 SQL；每个分析任务的成功、失败和未处理条数可追溯；导入同一 CSV 不重复计入；失败保留此前成功结果；证据偏移合法率 100%；无效输入不得静默截断。

当前证据：扫描范围循环依赖为 0，NLP 到 Web/API/DB 运行时依赖为 0；Controller 和业务服务直接 SQL 为 0，已定义层间依赖违规为 0。重构后完整验证为 49 项单元/集成测试、13 项端到端测试通过，涵盖 CSV 中文列映射、鉴权、去重、任务、复核、证据与浏览器受控页面；这不是代码覆盖率 100%，也不是所有电商实站均能采集。

性能建议验收环境固定为本机硬件，分别测 100、1000、5000 条评论下的导入、分页、统计接口 P50/P95、峰值内存与批量吞吐。可先以分页/汇总 P95 ≤ 1 秒、1000 条导入 ≤ 5 秒为项目目标；本轮执行 `npm run benchmark:queries`，内存 SQLite 合成夹具下 100/1000/5000 条仓储完整读取与六方面聚合的 P95 分别约 1.38/12.25/84.55 ms，1000 条 importRows 约 18.27 ms。20 次预热后采样，原始结果见[查询性能验证.json](架构图/查询性能验证.json)。这不含 HTTP、磁盘数据库、文件解析或模型推理，不可当作上述接口性能目标已通过。语义模型允许单条总上限 180 秒，单 Worker 防止批次并发把本地显存耗尽；批次耗时与评论长短及模型生成量有关，不承诺固定速度。

### NLP 质量与运行指标

固定口径：方面 micro P/R/F1；方面-情感对 micro-F1 与按有支持类别计算的 macro-F1；逐类支持量与分数；完全匹配率；待复核率；请求失败率；证据子串合法率；成功调用函数耗时 P50/P95。失败样例计入质量统计，不能通过过滤失败抬高结果；耗时分位数当前只包含成功调用并不包含入库/网页展示。

历史 42 条人工对照样例（absa-v2，非真实买家数据）：

- MNB：方面 F1 98.04%，方面-情感对 micro-F1 78.43%，macro-F1 77.01%；失败 0/42；P95 0.46 ms。
- MNB + 规则：方面 F1 98.04%，方面-情感对 micro-F1 79.55%，macro-F1 75.39%；待复核方面评价 27.45%；P95 0.36 ms。
- Qwen3：方面 F1 85.39%，方面-情感对 micro-F1 74.16%，macro-F1 55.46%；失败 3/42；成功调用 P95 2516 ms。

这些指标可从 [模型对照结果.json](实验结果/模型对照结果.json)复算。该小样本上 Qwen 没有优于基线，不能因为“大模型”就宣称更准确；选择它是为扩展复杂语义处理能力，但收益必须用真实独立测试证明。历史参数计数训练耗时约 2.03 ms，仅为 train 函数计时，不含启动、读文件与写文件。

建议下一次验收先建立不少于 300 条真实授权评论的独立标注数据；按产品、来源或时间分组切分并在切分前去重，两人独立标注、第三人裁决分歧。冻结测试集，再比较语义、pure MNB、混合基线和规则；单独报告反讽、否定、同方面混合、跨句、未提及及长度分层结果。可设端到端 micro-F1 ≥ 0.80、macro-F1 ≥ 0.75、技术成功率 ≥ 95% 为初始项目目标，但这属于待验收目标，当前 absa-v4 真实数据尚无结果。
