## 1. 当前系统到底靠什么分析

当前实现有两条纯文本 NLP 路径：本地 Ollama 文本模型结构化抽取（semantic），以及固定方面词典、字符 n-gram、多项式朴素贝叶斯（MNB）和规则的基线（hybrid/rules）。六个方面不变；语义模式读取完整评论，不依赖先命中方面关键词。

没有使用图像/音频输入、多模态模型、在线付费 API、BERT 微调、RAG 或向量数据库。TypeScript 后端通过 HTTP 调用本机 Ollama；Ollama 加载下载的预训练权重执行推理。项目自行训练的仍是 MNB 基线。两者不能混写为“本项目训练了大语言模型”。

语义接口、输出验证、批次任务与页面已实现；本机已在指定目录部署Ollama/Qwen3，并完成126条MNB训练与42条固定合成检查集实际对照，详见[模型对照实验报告](模型对照实验报告.md)。首轮和状态提示修正后的复测分别留存；这些是工程检查，不是独立真实领域评估。首次部署命令见 README。Ollama 支持在 format 中指定 JSON schema，见[官方结构化输出文档](https://docs.ollama.com/capabilities/structured-outputs)；schema 约束格式，不能保证语义正确。

以下分工专指保留的基线：

- 方面识别：现有代码使用词典与正则表达式；不是训练出的方面识别神经网络。
- 情感候选：一个共享三分类 MNB 模型产生正面/负面/中性候选。方面名称标记也参与字符特征；不是六个独立模型。
- 最终判断：领域规则明确命中时优先于模型候选；规则未覆盖时才采用模型，或将低分差的意见标为待复核。
- 混合情感：在评论层聚合同方面的正负局部意见，是后处理；不是 MNB 的第四个训练类别。
- 原文证据：通过子句起止索引获取原文片段；不是由生成式模型编造说明。
- 产品比较：对已保存意见做 SQL/应用统计；没有另一个“选购大模型”。

因此基线的准确名称是“规则与字符特征朴素贝叶斯结合的方面级情感分析基线”。其中规则起主要作用。教学检查集上基线混合系统和规则对照成绩相同；该成绩不属于本地文本模型。

## 3. CSV 可以从哪些网站找

CSV 是文件格式，不是数据来源。下载的数据可能是 ZIP、JSONL 或 Parquet，需要整理为本系统规定的列。下面按适用性说明，不能混用为“现成中文耳机方面级训练集”。

### 3.1 GitHub：ChineseNlpCorpus 的网购评论

[数据集目录](https://github.com/SophonPlus/ChineseNlpCorpus/tree/master/datasets/online_shopping_10_cats)和[作者说明文件](https://github.com/SophonPlus/ChineseNlpCorpus/blob/master/datasets/online_shopping_10_cats/intro.ipynb)。

仓库介绍为十类商品/场景、六万多条中文评论，字段为 cat、label、review。cat 是商品类别；label 是整条评论正负标签；review 是文字。类别包括手机、平板、计算机等，但该清单没有专门的耳机类。数据说明还指出部分原始来源不详，应进一步核实使用条件。

适合：学习中文整句情感分类、练习 CSV 清洗。限制：没有六方面标签，没有中性标签，也不能假定存在具体耳机型号。不要把手机或计算机评论包装成某款耳机的产品画像。

取得文件步骤：进入目录 → 阅读说明和下载链接 → 下载归档/CSV → 查看实际字段 → 记录版本与来源 → 按目标任务筛选和标注。此次只核实目录与说明，未下载全部归档。

### 3.2 Hugging Face：中文 Amazon 评论

[SetFit/amazon_reviews_multi_zh](https://huggingface.co/datasets/SetFit/amazon_reviews_multi_zh)。页面可预览中文文本，当前展示 id、text、label、label_text，文件格式为 JSON，并提供 train/validation/test 划分。

适合：了解真实中文评价表达，筛选含耳机相关内容后重新标注，或做通用情感实验。限制：当前这个重打包版本的展示字段没有商品型号/产品 ID，也没有方面标签；不能据此恢复具体耳机型号并进行真实型号对比。评级标签的含义应按当前版本说明核对，不要把数值直接当本系统的三类标签。

这个数据集缺少可靠的商品身份，不接入当前具体耳机画像/对比数据链路。课程系统采用用户提供的具体商品CSV或浏览器采集的商品评论；下载通用语料可用于独立情感研究，但不能冒充具体型号评论。

```powershell
npm run prepare:data -- --input data/raw/authorized-product-reviews.jsonl --output data/raw/product-comments.csv --product jd-100239311413 --source "已核对商品归属的授权评论" --contains "耳机,耳塞" --limit 500
```

工具只筛候选并保留原文，不自动添加方面标签或恢复缺失型号。支持本地JSONL或授权HTTPS文件地址，转换时不能覆盖已有文件。

[官方项目页面](https://amazon-reviews-2023.github.io/)。Electronics 提供评论与商品 metadata；官方字段包括 text、rating、asin、parent_asin，metadata 有 title 和 categories。适合通过商品元数据筛出耳机，再关联该产品评论。

## 4. 分析 CSV 和训练 CSV 是两种不同文件

### 4.1 分析导入 CSV

这是已经有模型后，要交给系统分析的评论，不需要人工标签：

```csv
productId,reviewId,text,source
my-earphone,r001,"音质很好，但戴久了耳朵疼。",教学格式示例
my-earphone,r002,"通话很清晰，不过续航太短。",教学格式示例
```

先创建 my-earphone 产品再导入。示例文字是合成示例。模板不是唯一格式：支持中英文列名自动识别和手工映射，正文必选，编号缺失时生成指纹编号；产品缺失须统一指定产品/集合。支持 UTF-8、GB18030/GBK 编码，错误解码提示重选。上限5000条、每条5000字、5MB，原文不截断。

原始列映射：原评论编号 → reviewId；原评论正文 → text；可核实的原产品标识经映射后 → productId；来源记录 → source。没有产品身份时不能编造真实型号。导入时还要填写来源说明与教学标记。

上传后发生的是 CSV 校验、去重、入库和运行现有模型。不会自动改变模型参数。

### 4.2 有监督训练 CSV

训练需要人的真值标注：

```csv
aspect,text,label
sound,音质很好,positive
comfort,戴久了耳朵疼,negative
battery,支持无线充电,neutral
```

这里 text 是方面相关局部片段；同一评论可拆成多个训练行。方面使用 sound/noise/comfort/battery/call/latency，标签使用 positive/negative/neutral。实际训练脚本要求每类至少三条，这是防止空类的程序检查，不代表达到模型质量所需的数据量。

“有续航功能/支持充电”是功能描述，不等于正向满意；“很一般”可按规范归中性；同一方面正负冲突的完整评论应在端到端真值中标 mixed，局部训练仍分别保留正负片段。

商品总星级和整句正负标签不是各方面的真值。例如五星评论也可以包含舒适度负面，不能把六个方面都标成正面。

### 4.3 真实数据准备流程（尚待开展）

确定来源权限 → 保留原始数据和来源记录 → 产品/语言/领域筛选 → 删除空文本与去重 → 试标并制定规范 → 双人标注部分样本及仲裁 → 按原评论和近重复组划分训练/验证/测试 → 只用训练集建立词表和模型 → 验证集调规则/阈值 → 冻结独立测试集 → 评价和错误分析。

同一评论不同片段不得分到训练和测试两边；先检查近重复再划分。人工修订也不能悄悄混入已冻结测试集。当前项目没有自动划分/完整标注工具，这些步骤需要团队实际执行并留档。

## 5. 模型究竟怎样训练

实现文件：packages/nlp/model.ts；训练入口：scripts/train.ts；内置样例：packages/nlp/training-data.ts。

### 第一步：读取带标签文本

默认使用内置 126 条教学样例；也可读取 aspect,text,label CSV。训练脚本验证方面和标签，然后调用 train()。

### 第二步：文本变成数字特征

当前特征处理：小写化、去掉空白与部分标点，按 Unicode 字符枚举连续的一字、二字、三字片段，统计出现次数。模型输入还拼接方面标记，例如 sound。

以“音质清晰”为例，省略方面标记：一字为“音、质、清、晰”；二字为“音质、质清、清晰”；三字为“音质清、质清晰”。这些片段的频次组成稀疏特征。未采用 jieba、词向量或 TF-IDF，报告不要写错。

### 第三步：按类别累计

对三类分别记录样例数 Nc、类别内所有特征总频数 Tc、每个特征频数 count(f,c)。词表是训练输入出现的特征集合 V。内置语料每类 42 条，总共 126 条。

### 第四步：估计概率

P(c)=(Nc+1)/(N+3)。P(f|c)=(count(f,c)+1)/(Tc+|V|)。加一平滑防止某个没见过的特征让概率变成零。

新片段的类别分数为：score(c)=log P(c)+Σ count(f,x)×log P(f|c)。只计算训练词表内特征，得分最高的类别作为候选。

这是真正的有监督频数学习，但不是神经网络训练：没有反向传播、epoch、GPU 或预训练权重下载。用 TypeScript 实现核心计数和预测，没有实际引入曾在方案调研中提到的 ml-naivebayes 库。

### 第五步：保存和加载

运行 npm run train 生成 data/model.json，保存 vocabulary、classes、trainingExamples、dataKind 和由训练数据生成的版本哈希。启动服务和 Worker 时加载、检查该文件；不存在时用内置样例建立教学模型。

替换模型文件后重启服务，并对旧批次重新分析，当前版本会生成新预测。旧版本预测保留；人工纠正只是有效视图的覆盖记录，不会自动训练。

真实训练文件准备好后，可在项目目录执行：

```powershell
npm run train -- --data data/authorized-train.csv --kind "授权真实训练集"
```

该命令会覆盖默认 data/model.json，请先保留旧模型。可加 --output data/models/real-v1.json 单独导出，再在 .env 里设置 MODEL_PATH 并重启。不要把验证和测试文件作为训练输入。

## 6. 基线单条评论怎样从输入得到结果

输入：“音质很好，但戴久了耳朵疼。”

1. 浏览器发送 POST /api/analyze，带 text 与 mode；服务器检查空值、长度和请求频率。
2. splitClauses() 根据标点和转折分为“音质很好”“戴久了耳朵疼”，并保留原文起止索引。
3. ASPECT_PATTERNS 匹配词典：音质/声音/低音等归 sound，佩戴/耳朵/夹耳等归 comfort。
4. 每个相关片段调用 predict() 得到 MNB 正/负/中性候选。
5. rulePolarity() 识别“很好”“耳朵疼”等规则，明确命中时采用规则结果；保护“不差、没有延迟、无杂音”等固定表达，避免看到“不”就判负面。
6. 无规则且模型最高分与第二高分间隔小于 3 时进入待复核；多方面共享难归属意见或同片段正负冲突也待复核。阈值 3 是当前教学启发式，未完成真实验证集校准。
7. 汇总同一方面：不同子句同时正负则 mixed；待复核与中性、未提及区别处理。
8. 返回方面、情感、证据、状态、方法与模型版本。前端按 UTF-16 左闭右开索引高亮原文。

结果为音质正面、舒适度负面，其余未提及。单条体验不写入产品统计。

代码还存在一个需要如实说明的细节：规则对照模式内部仍计算 MNB 候选，但无规则命中的意见始终标为待复核，不把模型候选当作规则已判定结果。因此这里比较的是最终规则决策口径，不是证明完全没有执行分类器计算的运行时基准。

## 7. 一批 CSV 怎样得到画像和对比

登录 → 上传文件并选编码 → csv-parse 读取表头 → 自动/人工映射 → 指定产品/集合和来源 → 校验去重并预览 → SQLite 事务入库 → 按所选方法创建任务 → Worker 调 analyzeSemantic() 或 analyze() → 保存版本化结果 → 画像与原文。模型连接失败不降级；单条失败记入 job_errors，其余继续；失败批次可重试，成功结果保留。

画像不是模型凭空生成的结论。每条评论每方面最多计一次；分母为正面、负面、中性、混合的已判定评论数。待复核和未提及不进入分母。按需求比较只是突出相关维度，并展示样本数和证据，没有独立推荐大模型。

### 7.1 本地文本模型如何理解多元评论

源码 packages/nlp/semantic.ts，默认 qwen3:4b。[模型页](https://ollama.com/library/qwen3)标为 Text，4B 版本下载约2.5GB。TypeScript 调用本机 POST /api/chat，传入完整评论、固定任务提示与 JSON schema，由 Ollama 加载预训练权重推理。temperature=0、think=false、stream=false；请求180秒超时。没有多模态输入或本项目神经网络训练；设备会影响速度，本机函数调用时延和设备状态已实测，见模型对照实验报告。

任务提示要求考虑否定、转折、比较、指代、隐含评价、反讽与同方面情境冲突。输出每方面情感、classified/review、表达方式 explicit/implicit/irony/uncertain、强度 low/medium/high、原文证据和简短理由。例如“音质不错但戴久疼”是两个方面分别正负；“办公室降噪不错，地铁却很吵”可能是降噪混合。它们是任务说明，不是已验证真实模型正确预测。

服务器检查枚举、重复方面和证据结构，定位原文证据后生成 UTF-16 索引；证据不存在则分析失败。mixed 没有正负双方证据、expression=uncertain 时转待复核。强度不是正确概率，理由由模型推断，必须核对原文。结构约束不保证语义正确。输入评论作为数据包传入，不作为系统指令；提示约束不等于完全防御提示注入。

工程版本记录模型标签和提示版本 absa-v2（首轮absa-v1归档）；正式实验还要记录 Ollama 版本、权重 digest、量化配置、硬件、数据版本，因为标签本身不固定权重。统计采用每条评论最近一次成功分析，可能包含不同方法，页面明确提示；方法效果比较应使用隔离数据统一分析口径。

### 7.2 训练、推理与评价边界

上传分析 CSV 不需要标签，执行推理，不自动训练。MNB 用 aspect/text/label 真值训练，公式和命令见第5节。Qwen3 由提供方预训练，本项目没有微调；提示、schema 和证据验证属于任务适配，不是参数学习。

若课程明确要求深度模型训练，仍需额外真实标注集与微调实验。当前 MNB 提供自行训练的对照路径；真实泛化需要独立测试。复杂评价应覆盖显式、隐含、否定、反讽、比较、指代和情境冲突，报告方面F1、方面—情感F1、证据匹配、待复核覆盖率和各类错误；已开展固定合成检查集上的本地实际模型对照，尚未开展独立真实领域评估。

## 8. 整个 Web 系统从 0 到 1 的实际步骤

### 8.1 需求与边界

确定用户、六方面、八项核心功能、输入上限、权限、异常与验收方法。将需求—接口—模块—测试建立对应关系。产物为方案和需求规格文档。

### 8.2 建立 TS 工程

在 ear-review 创建 package.json、TS 配置、Vite 配置和 apps/packages/scripts/data 目录。此次为手工搭建结构，没有声称使用 Nest CLI 自动生成。npm install 安装依赖，package-lock.json 固定解析后的版本。

### 8.3 先实现共享契约与 NLP

packages/contracts 定义方面、情感、证据、评论、画像、导入与任务类型；NLP 包实现字符频数分类器、方面词典、规则分句和意见聚合。编写训练/评价脚本，避免界面先完成却没有实际分析逻辑。

### 8.4 实现数据库

Store 使用 Node 内置 SQLite DatabaseSync，创建产品、批次、评论、预测、修订、任务和管理员表。参数化 SQL 防注入，事务保证导入原子性，外键与唯一键保持一致性，迁移补充批次概要字段。

### 8.5 实现 NestJS 服务

Controller 负责 REST 路由、参数检查和业务编排。Auth 用 scrypt 保存密码哈希，Bearer 会话控制写权限。预览 token 防止无校验提交；后台 Worker 执行批次计算。健康、模型、分析、评论筛选、统计、对比、复核和导出都是真接口。

### 8.6 实现 Vue 前端

Vue 3 + Vue Router + TypeScript + Vite。四个入口围绕 NLP 结果组织。AnalysisResult 展示方面列表，EvidenceText 按偏移高亮，ReviewList 提供筛选结果与复核。自定义 CSS 实现浅色响应式布局和带计数的堆叠条，lucide-vue-next 提供图标。

本版本没有采用 Pinia、Element Plus、ECharts 或 Prisma；这是已记录的轻量裁剪，报告应写实际栈。

### 8.7 训练/导出与教学验证

npm run train 保存模型；npm run evaluate 使用 24 条教学检查集计算方面与方面—情感 micro-F1，并保存每类支持数与错误案例。该脚本默认评价教学集，没有自动完成真实数据划分和真实测试。

### 8.8 软件测试

当前测试数量见课程报告第6章。Playwright 使用本机 Chrome 和隔离数据库验证浏览器/API流程。检查多方面、否定、证据索引、导入、去重、鉴权、任务、复核、导出、重启和移动布局。截图来自实际运行。

### 8.9 构建与部署

npm run build 先进行后端 tsc 和前端 vue-tsc 类型检查，接着编译服务器、Vite 构建浏览器资源。npm start 启动 NestJS，提供 API 和静态前端。监听 127.0.0.1:3001。本项目是本地部署，没有发布云端网站。

### 8.10 工程报告

记录实际技术、数据与局限；关联需求规格、源码、测试 JSON、教学评估、性能冒烟和真实页面截图。报告正文不能把公开数据候选写成已下载数据，也不能把方案目标值写成已测成绩。

## 9. 使用的资源与方法清单

- 软件运行/语言：Node.js、TypeScript、tsx；服务器 JavaScript 来自 TS 编译。
- 前端：Vue 3、Vue Router、Vite、自定义 CSS、Lucide 图标。
- 后端：NestJS、Express JSON 解析、reflect-metadata/RxJS 框架依赖。
- 数据：SQLite、参数化 SQL、事务、WAL、SHA-256 去重、CSV 解析和 UTF-8 导出。
- NLP：字符频数特征、多项式朴素贝叶斯、加一平滑、方面词典、情感规则、否定/转折处理、混合聚合、拒判与原文偏移。
- 认证：Node crypto、随机初始密码、scrypt、短期 Bearer 会话。
- 并发：Node worker_threads，分析任务和版本化 upsert。
- 验证：Vitest、Playwright、本机 Chrome、教学检查集与性能冒烟脚本。
- 方法参考：[方面级情感任务论文](https://aclanthology.org/S14-2004/)；工程结构依据现有需求/设计说明。
- 数据资源：上述站点是数据源链接和转换候选，未下载真实数据用于成绩。基线不依赖预训练权重；语义模式需下载 Ollama 文本模型。
