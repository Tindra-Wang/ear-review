# 模型与技术栈选型说明

核对日期：2026-10-12。本文记录三人课程项目的工程决策及取舍；不把厂商宣传或未完成的实验写成项目效果。权重目录、CPU/GPU、训练公式、结果和复现命令见 [模型运行训练与测试](模型运行训练与测试.md)。

## 1. 选型依据

项目的已知约束是三人课程大作业、业务代码使用TypeScript、Web界面简洁、支持自己的CSV导入，以及软件工程报告可解释和可追溯。核心任务是六个固定耳机评价方面的情感分析，而不是通用聊天或图像识别。

因此决策目标是：打通真实数据输入到结构化意见的流程；支持完整上下文和多方面正负差异；保留可解释的训练对照；减少演示部署服务数；能够核对原文、来源、模型版本和错误。算法效果仍需要真实独立领域评估，不能仅凭选型保证。

## 2. 为什么选择 Qwen3-4B

### 2.1 中文上下文任务与规模取舍

官方将Qwen3-4B定义为因果语言模型，提供预训练和后训练权重，支持多语言及思考/非思考模式。选择它作为中文评论的候选基础模型有公开技术依据，但其公开能力介绍不等于本项目反讽、隐含评价或方面抽取的准确率。[官方模型卡](https://huggingface.co/Qwen/Qwen3-4B)。

项目希望从“戴着开会，对方让我重复三遍”这类没有直接通话关键词的上下文中抽取候选意见；生成式文本模型可以将任务描述和完整评论作为输入，输出多方面结构，而基线主要依赖词典和局部片段。选择更灵活的模型是为了实验这种能力，不是已证明它总能正确理解人的情感。

默认4B而不是更大模型，是课程本地部署的成本折中。当前Ollama版本约2.5GB、Q4_K_M量化；较小产物降低下载与存储负担。本机有约8GB独立显存，但长上下文、缓存和运行缓冲仍可能限制GPU加载，不能仅比较模型文件与显存大小。[实际发布标签](https://ollama.com/library/qwen3:4b)。

没有在真实领域比较4B、8B或其他家族，因此不能写成“经过全面评测的最优模型”。默认标签可以通过OLLAMA_MODEL替换，但适配新模型时必须验证think参数、schema服从、输出校验和真实效果。

### 2.2 为什么本地部署

本地推理可以在权重下载完成后用本机服务运行，无需按请求付费的在线API密钥，方便课程现场复现和保留评论在本机。代价是每台演示机器要准备Ollama和权重，速度、驱动和内存需要验证。只有配置为本地地址且使用本地标签时，“评论留在本机”才成立；修改成远端服务后数据流向随之改变。

在线模型同样可以执行NLP，甚至可能有更好的语义效果；未选在线接口主要因为网络、账户、费用和复现条件，不是因为在线方式不属于NLP。项目没有进行本地与在线准确率或总成本实测。

### 2.3 为什么使用 Ollama

Ollama负责下载、加载和推理，应用只需调用HTTP接口，减少自行维护分词器、权重加载、推理后端和GPU环境的工作。其本地接口可通过JSON schema约束响应，适合本系统固定输出结构。[官方结构化输出说明](https://docs.ollama.com/capabilities/structured-outputs)。

这种结构允许TypeScript后端检查方面枚举、标签、重复方面和原文证据，再写入数据库。schema仅约束结构，不能防止语义误判；服务器子串检查也不能证明证据真的支持情感。保留待复核、原始结果和人工修订就是为处理这些限制。

当前使用非思考模式与低温结构化解码，是为了控制输出和等待时间的工程选择，尚未做质量/时延参数对比。请求180秒超时也是保护边界，不是实际模型速度保证。

### 2.4 局限及替换条件

本地生成模型仍可能误判反讽、比较对象、跨句指代、情境变化和程度，也可能遗漏方面。量化可能影响质量。固定六方面未覆盖的价格、物流、售后等意见不能硬塞到已有方面。

如果真实测试表明4B召回或证据质量不足，可先比较更大候选、提示和上下文设置；如果推理太慢且固定标签需求明确，可考虑训练编码器模型。如果课程要求深度训练，需要增加独立微调实验，不能仅更换更大预训练模型。替换依据应是冻结测试集的质量、资源和时延记录。

## 3. 为什么同时保留 MNB 与规则

保留基线有三个用途：展示项目自行训练的算法过程；解释频数学习与规则决策；为复杂模型提供可复现对照。字符特征不需要额外中文分词工具，当前126条教学样例即可检验计数、序列化、预测和拒判逻辑，CPU可执行。

它的优点是产物小、训练实现短、预测逻辑透明，易于在软件工程报告中给出公式和错误原因。代价是词典范围固定、局部特征难理解复杂上下文，教学小语料不能保证真实泛化。规则帮助处理领域否定和明确评价，也可能掩盖模型本身的贡献。

现有24条检查集上hybrid与rules的端到端F1相同。因此保留基线的依据是工程可解释性和对照价值，不能宣称实验已经证明它增强了规则，更不能据此证明Qwen3优于基线。

## 4. 为什么采用这套 Web 技术栈

### 4.1 Vue 3、Vue Router 与 Vite

Vue 3负责响应式表单、评论筛选、进度和结果更新；Router组织分析、画像、对比、工作台四个任务入口；Vite负责开发服务器和构建。现有AnalysisResult、EvidenceText、ReviewList和ImportMapping组件边界与用户任务对应，便于三人分工。

Vue提供TypeScript使用方式，组件契约可与后端共享。项目通过vue-tsc做类型检查，不能将Vite的代码转换当作完整类型验证。[Vue官方TypeScript说明](https://vuejs.org/guide/typescript/overview.html)。

使用自定义CSS和直接绘制的分布条，是为了让六个固定维度、样本数和证据保持简洁，减少组件库及复杂图表配置。当前没有采用Pinia、Element Plus或ECharts；Vue响应式状态已经覆盖此规模的页面需求。随着状态复杂度增加可以重新评估，不能说这些库普遍没有价值。

### 4.2 NestJS 与 Node.js

后端需要明确的路由、鉴权、输入验证、错误处理和生命周期，NestJS提供模块与依赖注入等组织方式，并以Node.js运行。[NestJS官方介绍](https://docs.nestjs.com/)。

选它是为了让课程报告能清楚对应Controller、Auth、Store、Worker与共享契约；普通Express也可完成这些功能，但会需要团队自己制定更多组织规范。当前代码仍有较集中的Controller和页面状态，采用框架本身不等于已经达到大型系统的模块化质量。

Node.js原生fetch调用Ollama；crypto提供指纹、随机令牌和密码哈希；worker_threads把基线批次计算放到Worker，并执行串行语义调用。Worker没有把模型权重移到JavaScript，也不能消除主线程同步数据库操作的阻塞。

### 4.3 SQLite 与参数化 SQL

课程演示以单机、小规模评论和低并发为边界。SQLite文件数据库减少额外服务安装，便于持久化批次、预测、修订和任务；事务、外键及唯一约束可检验导入一致性。本项目实际使用Node v24.14.0的DatabaseSync，运行时有实验性提示，不能用其他Node版本的API状态替代实际环境。

直接参数化SQL使字段、复合主键和版本查询清楚，没有引入Prisma。优点是依赖少、数据库设计可直接核对；代价是迁移和查询维护由团队负责。同步查询及当前逐评论查询方式不适合直接宣称高并发或大数据性能，规模扩大时应评估批量查询、异步数据层和其他数据库。

### 4.4 CSV、共享类型与测试

csv-parse处理引号、逗号和多行正文，避免手写split(',')导致真实CSV解析错误。ColumnMapping和ImportPreview等类型在前后端共享；前端还支持UTF-8与GB18030解码。原文保持可核对，输入上限和字段归属由服务器验证。

Vitest用于算法、映射、版本隔离等核心逻辑；Playwright验证浏览器上传和API闭环。采用两层测试，是为了区分“函数逻辑正确”和“用户流程能走通”。模拟模型返回只测试协议，另需真实模型效果实验。

## 5. 为什么用 TypeScript，不用 Python

### 5.1 首先来自已确定的需求

用户已明确“三人课程大作业，用TypeScript语言”。技术选择首先遵守这个项目约束。不能把后续选择描述为语言性能排名，也不能隐去需求来源。

### 5.2 适合当前工程工作

本项目的大部分工作是Web界面、CSV与表单、REST接口、数据库、任务编排和模型服务集成。前后端共享AspectId、Sentiment、Analysis、Evidence、Review等契约，可以减少字段名和标签不一致。一个团队使用一套主要语言、npm锁文件和类型检查命令，降低三人课程项目的环境与交接成本。

TypeScript在开发时提供类型检查，生产代码仍由JavaScript运行时执行；类型会在转换过程中被移除，不自动验证网络请求或模型返回。因此后端仍保留显式参数、schema语义和原文证据检查。[TypeScript官方说明](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html)。

MNB的核心是字符计数和概率计算，无需深度学习框架；用TypeScript实现能展示真实算法过程。Qwen3的重运算由Ollama承担，调用方使用TypeScript还是Python并不决定模型参数在GPU上的计算速度。项目没有进行两种语言运行效率实验，不能声称TypeScript比Python更适合所有NLP任务。

### 5.3 Python 更适合哪些后续工作

如果重点转为训练/微调神经网络、批量科学计算、数据探索和实验可视化，Python的主流工具与训练工作流更合适。现阶段没有这些深度训练代码，不需要为了HTTP模型调用再增加Python服务。

后续增加PyTorch/Transformers等训练工具时，应将其作为独立训练子项目，产物或服务通过接口提供给TypeScript Web；这不会要求重写整个前端和业务后端。若课程要求所有提交代码严格限定TypeScript，则引入Python前需核对课程边界；目前项目只有TypeScript业务与训练脚本。

### 5.4 这个选择的代价

TypeScript并非主流深度模型训练语言，本项目没有用它重写神经网络训练框架。省去Python环境降低当前部署复杂度，也意味着没有现成的深度微调流水线。它满足当前Web系统与MNB训练范围，不自动满足“必须自行训练大语言模型”的额外要求。

## 6. 三人协作与后续决策

建议前端成员负责CSV映射和结果/证据展示，后端成员负责鉴权、数据与任务，NLP成员负责来源与标注规范、基线训练、语义部署和真实评价。三人共同维护共享契约与报告事实；这是分工建议，不是已经完成的成员贡献记录。

当前选型的验收顺序是：上传闭环与错误处理 → 本地权重部署和实际设备确认 → 独立标注集 → 方法对比 → 性能与资源测量。现阶段已完成上传流程、本地权重部署、实际100% GPU加载确认及固定合成检查集的同输入对照。首轮提示的全拒判问题与修正后的同集复测见[模型对照实验报告](模型对照实验报告.md)；独立真实标注集和全规模性能尚需补齐。选型可以随着真实数据和设备证据调整，不能把默认候选包装成最终最优结论。

报告可采用：“采用TypeScript统一Web业务与接口契约，Vue 3承担交互、NestJS组织服务、SQLite保存可追溯数据；Ollama隔离预训练模型运行时，Qwen3-4B作为资源可控的语义候选，MNB提供自行训练与解释性对照。选择依据是课程约束和工程成本，模型质量需由真实独立实验确认。”
